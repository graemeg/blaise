== Context

Blaise produces native executables for `linux-x86_64`, `freebsd-x86_64` and
`macos-arm64` with its own code generator, assembler and linker.  This
document specifies the addition of `windows-x86_64`.

FreeBSD was a cheap second target because it shares the ELF container and the
System V AMD64 ABI with Linux.  Windows shares neither.  It differs on four
axes at once:

[cols="2,3,3",options="header"]
|===
| Axis | Linux / FreeBSD x86_64 | Windows x86_64

| Image container
| ELF
| PE32+ (import tables, base relocations, TLS directory)

| C calling convention
| System V AMD64
| Microsoft x64 ("Win64")

| Thread-local storage
| `%fs`-relative, local-exec
| `%gs:0x58` TLS array indexed by `_tls_index`

| Kernel surface
| Stable syscalls (Linux), libc (FreeBSD dynamic)
| `kernel32.dll` and friends; syscall numbers are not stable
|===

The design goal is to add the target while changing as little existing code as
possible, and to do so entirely through the ports-and-adapters seams described
in `native-target-architecture.adoc`.

=== Scope

In scope:

* cross-compiling console and GUI-subsystem executables for Windows from any
  supported host;
* the always-linked runtime and the `TRtlPlatform` adapter for Windows;
* calling Windows DLLs, and being called back by them;
* self-hosting: a `blaise.exe` that rebuilds itself on Windows;
* the test infrastructure needed to verify all of the above from a macOS
  arm64 development host.

Out of scope for this document:

* Windows on arm64;
* producing DLLs (`library` modules) — executables only at first;
* linking third-party COFF `.obj` / `.lib` files;
* PDB / CodeView debug information;
* structured exception handling (SEH) interoperability;
* a GUI toolkit binding;
* the debugger itself.  Appendix A records only what the *compiler* must emit
  so that a later pdr port has what it needs.

=== Minimum Windows version

Windows 10 version 1809.  This guarantees `WaitOnAddress`, slim reader/writer
locks, `GetSystemTimePreciseAsFileTime`, and a console that honours the UTF-8
code page.

[#rule-no-ifdef]
== Governing rule: no conditional-compilation sprawl

Blaise does not express target differences with `{$IFDEF}` blocks woven
through shared units, and it has no include files.  The FPC model — hundreds
of conditionals and thousands of `.inc` files — is the explicit non-goal.
Target divergence lives in *which object is instantiated* or *which unit is
linked*, decided once.

Every Windows difference in this design is assigned one of those mechanisms:

[cols="2,4",options="header"]
|===
| Divergence | Mechanism

| Calling convention at the foreign-code boundary
| `TX86BoundaryAbi` strategy object, supplied by the target toolkit

| TLS access sequence
| `TX86TlsModel` strategy object, supplied by the target toolkit

| Image container
| A separate linker unit (`blaise.linker.pe`), selected by the toolkit

| Kernel surface
| Whole-unit substitution by name suffix in `BuildRTLUnitList`
  (`runtime.*.windows`)

| High-level OS operations
| `TRtlPlatformWindows`, an adapter behind the existing `TRtlPlatform` port

| Library-name mapping and library search directories
| Per-target methods on the toolkit, not `if Target.OS = …` chains in the
  driver
|===

The permitted uses of conditional compilation are the ones that exist today,
and no others are added:

* `HostTarget` in `blaise.codegen.target.pas`, which detects the OS the
  compiler binary itself was built for (the `WINDOWS` arm is already present);
* the CPU-keyed bodies in `runtime.atomic`, `runtime.setjmp` and
  `runtime.utf8`.

Two places invite a shortcut and must not take it:

* *The x86_64 backend.*  `blaise.codegen.native.x86_64.pas` contains no OS
  branch at all today.  It stays that way: it consults strategy objects.
* *The native driver.*  `blaise.codegen.native.driver.pas` already has
  `if ATarget.OS = osFreeBSD` chains (`LinkLibSoname`, `BuildLibSearchDirs`).
  These gain no third arm; they move behind the toolkit first (milestone M0).

Each milestone's review checklist includes: _search the diff for a new
`{$IFDEF WINDOWS}` or `osWindows` comparison outside the toolkit, the target
unit and the RTL unit-list builder; any hit needs a written justification._

== Current state

=== What already generalises

[cols="2,4",options="header"]
|===
| Component | State

| Target model (`blaise.codegen.target.pas`)
| `osWindows` exists; `ParseTargetName` accepts `windows-x86_64`;
  `ExecutableExtension`, `TargetDirectorySeparator`, `TargetPathSeparator`
  and `TargetLineEnding` already return `.exe`, `\`, `;` and CRLF.

| Conditional symbols (`Blaise.pas`)
| A Windows target defines `WINDOWS` and withholds `UNIX`.

| Toolkit and registry (`blaise.codegen.toolkit.pas`)
| A toolkit whose `MakeLinkTarget` returns `nil` is already understood by
  `LinkViaInternalLinker` as "not an ELF image" and is routed to a different
  linker.  macOS uses this; Windows slots in the same way.

| Internal x86_64 assembler (`blaise.assembler.x86_64.pas`)
| Emits ELF relocatable objects.  Under decision D2 this is reused unchanged.

| RTL unit selection (`BuildRTLUnitList` in `blaise.codegen.driver.pas`)
| OS-specific leaves are selected by name suffix (`RTLOSSuffix`).

| Freestanding runtime profile
| The Linux `--static` profile already shows how the core runtime runs with
  no libc: a small leaf set defines the POSIX-named symbols the core units
  bind.  Windows follows the same pattern.

| String encoding at the OS boundary
| Already ruled in `language-rationale.adoc` (_Windows Win32 / GDI_): UTF-8
  internally, conversion to UTF-16 inside RTL wrappers, `W` APIs only.
|===

=== What does not

[cols="2,4",options="header"]
|===
| Component | Gap

| `TargetUsesElf`
| Conflates "objects are ELF" with "the image is ELF".  For Windows the first
  is true and the second false, so the predicate must be split.

| Calling convention
| The System V register assignment appears at roughly 750 sites in 91
  procedures of the x86_64 backend, mostly hand-written sequences such as
  `movq …, %rdi` / `callq _StringRelease`.  The tables `SysVArgRegs*` and
  `SysVXmmArgRegs` cover only part of it.

| `TMethodDecl.CallingConv`
| Parsed and serialised to `.bif`, but read by neither the semantic pass nor
  the code generator.  The parser accepts `cdecl`, `stdcall`, `register`,
  `pascal` and `safecall` (`uParser.pas`, two sites) and treats them all as
  noise.  <<d5>> reduces the set to `cdecl`.

| TLS
| Every threadvar access is formatted as `%fs:sym@tpoff`, either as a direct
  memory operand or via `movq %fs:0` + `leaq sym@tpoff(...)`.  The assembler's
  `opTLS` operand kind knows only `%fs`.

| Stack growth
| No stack probing is emitted.  Windows commits stack pages through a guard
  page; a frame that skips the guard page faults.

| Import binding
| ELF dynamic linking needs only a list of libraries.  A PE import table
  needs the DLL *per symbol*.  `ExternalLib` is recorded per declaration in
  the AST but does not reach the linker.

| Runtime OS surface
| `rtl.platform.posix.pas` is the only `TRtlPlatform` adapter.  Its
  primitives (`fork`, `execvp`, `waitpid`, `pipe`, `stat`) have no direct
  Windows equivalent.

| Fault handling
| The runtime installs no signal handlers today, so there is nothing to port,
  but an unhandled access violation on Windows raises an error dialog unless
  the process deals with it.
|===

== Decision record

[#d1]
=== D1 — System V ABI internally, Win64 ABI at the boundary

*Decision.*  Blaise code compiled for Windows keeps the System V AMD64 calling
convention for every call between Blaise routines and from Blaise code into
the runtime.  The Microsoft x64 convention is used only where control crosses
into or out of foreign code.

*Alternative rejected: Win64 everywhere* (the FPC and Delphi approach).  It
would let any procedure pointer be handed to Windows unannotated.  It was
rejected because it requires re-plumbing argument assignment, shadow space,
aggregate passing and the callee-saved set through the whole 28,000-line
backend and providing Win64 variants of every inline-assembler routine in the
runtime — a second backend in all but name, and exactly the per-target
duplication the governing rule exists to prevent.

*Precedent.*  Go uses its own internal ABI on every OS and translates at the
C boundary.

*Cost accepted.*  A routine that Windows calls must be declared `cdecl`.  See
<<d5>>, <<d6>> and <<abi-language-rule>>.

[#d2]
=== D2 — ELF relocatable objects, PE linker

*Decision.*  ELF `ET_REL` remains the internal object format for
`windows-x86_64`.  A new linker consumes those objects and writes a PE32+
image.

*Rationale.*  Every object in a Blaise link is produced by Blaise (the RTL is
compiled from source), so the object format is a private matter.  Keeping ELF
reuses, unchanged: `AssembleToObject`, the per-unit object cache, `.bif`
embedding through `uElfObject`, `ReadElfObjectFile`, and
`CollectDefinedSymbols`.

*Alternative rejected: COFF objects.*  This needs a COFF writer and reader,
plus COFF variants of the cache, the interface embedding and the symbol scan,
for one benefit — linking foreign `.obj`/`.lib` files — that no current target
relies on.  A COFF *reader* can be added later without disturbing this design.

*Precedent.*  UEFI toolchains build ELF and convert to PE.

*Consequences.*

* `--assembler external` and `--linker external` are rejected for Windows
  targets with a clear message.  The emitted `.s` uses ELF directives that a
  COFF assembler does not accept.
* `uIfaceObject`'s stubbed PE section name (`.bliface`) stays unused.

[#d3]
=== D3 — Test on Windows 11 ARM64 under QEMU; real x64 in CI

*Decision.*  The local automated lane is a Windows 11 ARM64 guest under
`qemu-system-aarch64` with HVF acceleration, managed by UTM, which bundles the
guest drivers and provides the `utmctl` command line.  It runs x64 executables through
Windows' built-in x64 emulation, with the real loader and the real
`kernel32`.  Coverage on genuine x64 hardware comes from a GitHub Actions
`windows-latest` job.

*Alternatives rejected.*

* _Converting an existing x64 VirtualBox disk._  On Apple Silicon an x64 guest
  runs under full TCG emulation; boots take minutes and test runs are
  impractically slow.
* _Wine only._  Wine's loader is more forgiving than Windows', so a malformed
  PE header can pass there and fail on Windows.  It also depends on Rosetta 2,
  which is not installed on the development host and has a limited future.

Details in <<testing>>.

[#d4]
=== D4 — `WriteLn` emits CRLF

*Decision.*  On a Windows target `WriteLn` writes `LineEnding`, which
`language-rationale.adoc` already fixes as `#13#10`.

*Alternative rejected: LF on every target.*  It would make test output
identical across platforms but leave `WriteLn` disagreeing with the documented
constant, and differ from Delphi and FPC behaviour.

*Consequence.*  The e2e harness normalises CRLF to LF before comparing
expected output.

[#d5]
=== D5 — `cdecl` is the only calling-convention directive

*Decision.*  `cdecl` means "the platform C calling convention" and is the only
calling-convention directive in the language.  `stdcall`, `pascal`, `register`
and `safecall` become compile errors.  The message for `stdcall` and
`safecall`, which name a C-side convention, says to write `cdecl`.  The message
for `register` and `pascal`, which name the language's own convention, says to
delete the directive: writing `cdecl` there would turn a Blaise routine into a
foreign one under <<d1>>.  `winapi` is not added.  `varargs` remains and is valid only on a `cdecl`
routine.

*Reasoning.*  The distinctions between these directives exist only on 32-bit
x86, which Blaise does not target.  On every 64-bit target FPC and Delphi
accept them and ignore them, because their default convention already is the
platform C convention.  Keeping them would preserve legacy syntax with no
meaning, contrary to the language's design goal.  The concept itself is not
legacy: under <<d1>> the default Blaise convention on Windows differs from the
C convention, so exactly one marker is required.

*Alternative rejected: `cdecl`, `stdcall` and `winapi` as synonyms.*  Familiar
to FPC and Delphi users, but three spellings of one meaning, two of them named
after a distinction that no longer exists.

*Consequence.*  This is a target-independent language change.  It needs
entries in `docs/language-rationale.adoc` and `docs/grammar.ebnf`, a
migration-analyser rule, and a mechanical rename in Blaise Canvas UI (55 uses
of `stdcall`: 53 in its Win32 platform unit and 2 in its event-loop unit).
One of them, the window procedure, is a callback with a Blaise body; it is
correct only once foreign entries exist (M5).  The compiler, the runtime and
the standard library contain no use of the removed directives; the bindgen
tool already emits `cdecl`.  The `varargs` rule does reach them: five
library-less `varargs` bindings (`fcntl`, `open`, `ioctl`) gain an explicit
`cdecl`.

[#d6]
=== D6 — A named library implies `cdecl`; a library-less `external` does not

*Decision.*

* `external '<lib>'`, with or without `name`, declares a routine in a foreign
  library and has the C convention implicitly.
* `external name '<symbol>'` with no library keeps the Blaise convention
  unless `cdecl` is written.

*Reasoning.*  The convention of a call must be knowable from the declaration
alone; the code generator cannot wait for the linker to discover where a
symbol is defined.  Library-less externals are how the compiler and the
standard library reach runtime routines that are themselves written in Blaise
(`external name '_StrToDouble'`, `external name '_SolSocket'`), and how the
core runtime reaches its POSIX-named leaves (`write`, `mmap`).  All of those
are Blaise code and use the internal convention.  A routine in a named library
is by definition not in the Blaise image.

*Alternative rejected: `external` never implies a convention* (the FPC and
Delphi rule).  Every library binding would have to write `cdecl`, and
forgetting it would be a silent ABI defect on Windows only.

*Consequences.*

* A Windows DLL import always names its library, so it is always a C-convention
  call.  This matches the PE requirement that an import names its DLL.
* A Blaise routine that *defines* a symbol which other units bind through a
  named library must itself be declared `cdecl`.  The one known case is the
  `pthread_*` set: `runtime.thread` binds `external 'pthread'`, and
  `runtime.thread.windows` supplies the definitions.  See
  <<runtime-thread-windows>>.

[#d7]
=== D7 — A fatal fault exits with its NTSTATUS code

*Decision.*  When a hardware fault terminates a Blaise program on Windows, the
process exit code is the Windows exception code itself: `0xC0000005` for an
access violation, `0xC00000FD` for a stack overflow, `0xC0000094` for an
integer division by zero, `0xC000001D` for an illegal instruction.

*Reasoning.*  This is the direct analogue of exit code 139 on POSIX targets,
which is not a Blaise convention but the shell's encoding of "terminated by
`SIGSEGV`".  The NTSTATUS value is the operating system's own statement of how
the process died; it keeps the kind of fault distinguishable, and CI runners,
PowerShell and debuggers recognise it.  It is also what a C, C++ or Rust
program produces by default.

*Alternatives rejected.*

* _The FPC and Delphi runtime-error numbers_ (216 access violation, 202 stack
  overflow, 200 division by zero).  A Turbo Pascal inheritance that would need
  a Blaise-specific table.
* _One fixed code for every fault_ (Go exits with 2).  Loses the kind of
  fault.

*Consequence.*  The e2e harness gains a per-target "fault exit code" helper,
so tests that assert 139 today ask the harness instead of hard-coding the
number.  No test carries a conditional.

[#abi]
== ABI design

=== Internal convention

Unchanged.  Arguments in `RDI, RSI, RDX, RCX, R8, R9` and `XMM0–7`; callee
preserves `RBX, RBP, R12–R15`.  The inline-assembler runtime units
(`runtime.atomic`, `runtime.setjmp`, `runtime.utf8`) are valid as written.

Three obligations apply to *all* code on Windows regardless of convention.

Stack probing::
Windows grows a thread's stack by faulting on a guard page.  A prologue that
lowers `RSP` by more than one page and then writes below the guard page
faults instead of growing.  `BuildFrame` therefore emits a probe when the
frame is 4096 bytes or larger: touch one byte in each page from the old `RSP`
downwards before the final adjustment.  The probe is emitted inline; there is
no `__chkstk` import.  Whether a target needs probing is a Boolean property
of the boundary-ABI strategy (<<abi-strategy>>), not an OS test.

No red zone::
Windows may write below `RSP` when it dispatches an exception.  The backend
must not keep live data below `RSP`.  No red-zone use was found in the
survey, but this is an audit item for M0 because nothing has forbidden it
until now.

Stack alignment::
16-byte alignment at every `call`, as today.

[#abi-strategy]
=== The boundary strategy

A new abstract class, constructed by the toolkit and held by the backend.
The backend keeps the mechanics of a call -- evaluating each argument -- and
the strategy holds the convention's rules: where each argument goes.  As
built in M2:

[source,pascal]
----
type
  TX86ForeignArgKind = (fakInt, fakSingle, fakDouble, fakRecord);

  TX86ForeignArgLoc = record
    Reg: string;        { the register, or '' for the stack }
    MirrorReg: string;  { a second register (a variadic float), or '' }
    StackOff: Int;      { offset from %rsp at the call, when Reg = '' }
    ByRef: Boolean;     { a record passed as the address of a copy }
  end;

  TX86BoundaryAbi = class
  public
    { True when a reservation of more than a page must be probed. }
    function NeedsStackProbe: Boolean; virtual; abstract;
    { True when a C-convention routine differs from the internal one. }
    function ForeignDiffers: Boolean; virtual; abstract;
    { Home space plus stack-passed arguments for AArgCount arguments. }
    function ForeignOutgoingBytes(AArgCount: Int): Int; virtual; abstract;
    { Where argument AIndex travels. }
    function ForeignArgLoc(AIndex: Int; AKind: TX86ForeignArgKind;
      ASize: Int; AVariadic: Boolean): TX86ForeignArgLoc; virtual; abstract;
  end;
----

The inbound side -- the prologue and epilogue of a routine foreign code
calls -- is added in M5.

Two adapters:

* `TSysVBoundaryAbi` — `ForeignDiffers = False`; the foreign paths are never
  taken.  Used by Linux and FreeBSD.  Introducing it changes no emitted code.
* `TWin64BoundaryAbi` — implements the rules below.

The constraint is that the backend asks the strategy and never tests the OS.

A foreign call reserves one block below `RSP`: the outgoing area at the
bottom (32 bytes of home space, then the stack-passed arguments), one 8-byte
temporary per argument above it, and the copies of records passed by
reference above those, padded so the call site is 16-byte aligned.  Each
argument is evaluated, left to right, into its temporary; then the
stack-passed arguments and finally the registers are loaded from the
temporaries, so no argument's evaluation can disturb another's register.

Stack probes are emitted in the backend's `Emit` hook, through which every
`subq $N, %rsp` passes -- the prologue's frame and the body's argument and
buffer blocks alike.  A reservation of more than 4096 bytes becomes 4096-byte
steps, each followed by `orq $0, (%rsp)`, then the remainder.  A step of at
most one page lands at worst on the guard page itself, which grows the stack
as intended.  No register is needed.

=== Outbound calls (Blaise → foreign)

A call is foreign when the callee's declaration or procedural type has the C
convention: `cdecl` written explicitly (<<d5>>), or implied by
`external '<lib>'` (<<d6>>).  A library-less `external name` without `cdecl`
is an internal call.  Such calls
reach `EmitCall` (for a named routine) or `EmitCallIndirectEx` (through a
procedure pointer); both delegate to `EmitForeignCall`.

Win64 lowering rules:

* The first four arguments are positional.  Argument _i_ goes in
  `RCX, RDX, R8, R9` if it is an integer or pointer, or in `XMM0–XMM3` if it
  is a float.  An integer in position 2 uses `RDX` even if position 1 was a
  float.
* The caller reserves 32 bytes of shadow space above the return address, even
  for calls with fewer than four arguments.  Further arguments go on the stack
  above the shadow space, each in an 8-byte slot.
* An aggregate of exactly 1, 2, 4 or 8 bytes is passed by value in an integer
  register or slot.  Any other aggregate is passed as a pointer to a copy the
  caller makes.
* A result of 8 bytes or fewer is returned in `RAX`, or `XMM0` for a float.
  Any other aggregate is returned through a hidden pointer passed in `RCX`
  (ahead of the other arguments); the callee returns that pointer in `RAX`.
* For a variadic callee, a float passed in `XMM0–3` is also copied into the
  matching integer register.
* The callee preserves `RBX, RBP, RDI, RSI, R12–R15` and `XMM6–XMM15`.  This
  is a superset of what the internal convention assumes, so nothing extra
  needs saving around the call.

The record-return classifier in `blaise.codegen.native.backend.pas`
(`ClassifyRecordReturn`) implements System V classification; the Win64 rule is
simpler and belongs in the Win64 adapter, not as a branch inside the shared
classifier.

=== Inbound calls (foreign → Blaise)

A routine with a body that is declared `cdecl` is compiled with a foreign
entry.  Its prologue:

. saves `RDI`, `RSI` and `XMM6–XMM15`, which the caller expects preserved and
  the body is free to clobber;
. moves the Win64 arguments into the homes the body expects, exactly as if
  they had arrived in System V registers;

and its epilogue restores the saved registers and returns the result in the
Win64 location.

Uses:

* callbacks passed to Windows (window procedures, enumeration callbacks,
  `CreateThread` start routines);
* the runtime's own thread trampoline;
* the image entry point.

A Blaise exception must not propagate out through a foreign entry: the
Windows frames above it are not Blaise frames and the `setjmp`-based unwinder
would skip their cleanup.  This matches the existing rule for C callbacks on
other targets.

[#abi-language-rule]
=== Language rule: calling convention is part of the type

This is a language decision.  When it is implemented,
`docs/language-rationale.adoc` and `docs/grammar.ebnf` are updated in the same
commit, as the project rules require.

The rule, following <<d5>> and <<d6>>:

* `cdecl` is part of a routine's signature and of a procedural type.  The
  syntax is the one FPC and Delphi share:
  `type TCallback = function(X: Int32): Int32; cdecl;`.
* `cdecl` is the only calling-convention directive; the others are errors.
* `external '<lib>'` implies `cdecl`; a library-less `external name` does not.
* `varargs` requires `cdecl`.
* Assigning a default-convention routine to a C-convention procedural type
  (or the reverse) is a *compile error on a Windows target* and a *portability
  warning on every other target*, where the two conventions happen to
  coincide.

The warning on other targets is the valuable part: it tells a Linux developer
that a callback will not work on Windows before anyone tries.

[NOTE]
====
Migration items for the implementing session:

* Existing bindings (`net.sockets`, `runtime.thread`'s start routine, the
  bindgen output, Blaise Canvas UI) pass default-convention routines as C
  callbacks.  They will begin to warn.  The bindgen tool should emit `cdecl`
  on generated callback types as it already does on routines.
* Audit every library-less `external name` in the standard library that binds
  a genuine C library symbol (for example the socket calls).  On Windows each
  must either gain a library name or be supplied by a Blaise leaf unit.
====

=== Data model

Windows is LLP64: C `long` is 32 bits, where it is 64 bits on Linux, FreeBSD
and macOS.  This does not affect Blaise's own types, but it does affect
bindings.  The bindgen tool must map `long` / `unsigned long` by target, and
hand-written bindings that used `Int64` for a C `long` are wrong on Windows.

[#tls]
== Thread-local storage

=== Model

A PE image with thread-local data carries a TLS directory.  The loader
allocates a copy of the TLS template per thread and stores its address in a
per-thread array.  The image's slot in that array is written by the loader
into a variable the image names, conventionally `_tls_index`.

Access sequence:

[source,asm]
----
    movq  %gs:0x58, %r        # TEB.ThreadLocalStoragePointer
    movl  _tls_index(%rip), %ecx
    movq  (%r,%rcx,8), %r     # this image's TLS block for this thread
    # the variable is at  sym@tpoff(%r)
----

Offsets are *positive* from the start of the block, where on ELF x86_64 they
are negative from the thread pointer.

=== Strategy object

As built in M3:

[source,pascal]
----
type
  TX86TlsModel = class
  public
    { An operand for ASym that a caller may splice into any instruction. }
    function DirectOperand(const ASym: string): string; virtual; abstract;
    { Emit code leaving the address of ASym in ADstReg. }
    procedure EmitAddress(const ASym, ADstReg: string;
      AEmit: TX86EmitProc); virtual; abstract;
    { The backend's Emit hook, applied to every line before it is written:
      True after emitting a replacement for ALine. }
    function RewriteLine(const ALine: string;
      AEmit: TX86EmitProc): Boolean; virtual; abstract;
  end;
----

* `TElfLocalExecTls` returns `%fs:sym@tpoff`; its hook rewrites
  `leaq %fs:sym@tpoff, %reg`, which would yield the bare offset, into thread
  pointer plus offset — today's behaviour.
* `TPeTlsModel` returns a marker operand.  Its hook expands every line that
  carries one into the block load and the line itself:
+
[source,asm]
----
    movq  %gs:88, %r11           # TEB.ThreadLocalStoragePointer
    movq  (%r11), %r11           # this image's block: index 0
    <the line, with the marker replaced by sym@tpoff(%r11)>
----
+
`EmitAddress` loads the block into the destination register itself.

The register question the original design left open was settled as follows.
The backend splices operands into arbitrary instructions and reuses an
operand string across later instructions, including across calls, so a base
register loaded when the operand is formed could be stale or clobbered when
it is used.  Expanding at emission time instead reloads the base for every
instruction that uses it.  The base lives in `%r11`, caller-saved scratch
whose six live ranges in the backend were audited: none holds `%r11` across
a global variable's operand.  A line that uses `%r11` as well as the marker
is an internal error, never wrong code.

The access sequence assumes the executable's TLS index is 0, which saves the
second register an indexed load would need.  `runtime.start.windows` checks
`_tls_index` at start-up and stops with a diagnostic if it is not.

=== Assembler and linker

* The assembler's `opTLS` operand accepts `%gs:` with a numeric displacement
  in addition to `%fs:`, and accepts `sym@tpoff(%reg)` (already used by the
  `leaq` form).
* No new relocation kind is needed.  The PE linker resolves `crkTPOFF32` as
  _symbol address minus start of the merged `.tls` section_.
* `.tbss` is written out as zero bytes in the image and the directory's
  `SizeOfZeroFill` is 0.  Zero-fill has a history of being ignored by
  loaders; materialising the bytes removes the dependency.  (Confirmed in
  M3: the loader in Windows 11 on ARM sizes the block from the raw data
  range alone; with `.tbss` as zero fill, writes to threadvars corrupted the
  heap and the process crashed in `ntdll` at exit.)
* The linker synthesises `_tls_index` in `.data` and the TLS directory in
  `.rdata`, and points data directory 9 at it.

=== Thread exit

The TLS directory may list callbacks that the loader runs on thread attach
and detach.  One callback, defined in the Windows thread leaf, runs the
handlers registered through `_BlaiseThreadAtExit` on `DLL_THREAD_DETACH`.
This is the Windows counterpart of `__cxa_thread_atexit_impl` on Linux and
`_tlv_atexit` on macOS.  As a foreign entry it is compiled with the C
convention.

=== Image layout

DOS header::
Minimal `MZ` header with `e_lfanew` and the conventional stub.

COFF file header::
`Machine = 0x8664`; `Characteristics = EXECUTABLE_IMAGE |
LARGE_ADDRESS_AWARE`.

Optional header (PE32+, magic `0x20B`)::
* `ImageBase = 0x140000000`
* `SectionAlignment = 0x1000`, `FileAlignment = 0x200`
* `MajorOperatingSystemVersion` / `MajorSubsystemVersion = 6.0`
* `Subsystem = 3` (console) or `2` (GUI), from `--subsystem`
* `DllCharacteristics = HIGH_ENTROPY_VA | DYNAMIC_BASE | NX_COMPAT |
  TERMINAL_SERVER_AWARE`
* `SizeOfStackReserve = 8 MiB`, `SizeOfStackCommit = 64 KiB` — the reserve
  matches what Blaise programs get on Linux
* `AddressOfEntryPoint` = RVA of `_start`

Sections::
+
[cols="1,1,4",options="header"]
|===
| Name | Access | Contents

| `.text`
| R X
| Merged code, followed by the import thunks

| `.rdata`
| R
| Merged read-only data, import directory, import lookup tables, hint/name
  table, import address table, TLS directory

| `.data`
| R W
| Merged initialised data, then `.bss` as an uninitialised tail
  (`VirtualSize` greater than `SizeOfRawData`)

| `.tls`
| R W
| `.tdata` followed by `.tbss` as zero bytes

| `.blunw`
| R W
| Merged `blaise_unwind` blocks, bracketed by the start/end symbols the
  runtime walks (see `exception-unwind-cleanup-design.adoc`)

| `.opdf`
| R
| Merged OPDF debug records, when `--debug-opdf` is given

| `.reloc`
| R, discardable
| Base relocations
|===

Section names are limited to eight bytes, hence `.blunw`.

Data directories populated: import (1), base relocation (5), TLS (9), import
address table (12).

=== Relocations

[cols="2,4",options="header"]
|===
| ELF relocation | PE linker action

| `R_X86_64_PC32`, `R_X86_64_PLT32`
| Resolve directly.  If the target is an imported function, resolve to its
  thunk.

| `R_X86_64_64`
| Write `ImageBase + RVA` and record an `IMAGE_REL_BASED_DIR64` entry for the
  location.

| `R_X86_64_TPOFF32`
| Symbol address minus start of `.tls`.

| `R_X86_64_32`, `R_X86_64_32S`
| Link error.  A 32-bit absolute address cannot be rebased above 4 GiB.  The
  backend already emits position-independent code for Linux PIE, so none are
  expected; an occurrence is a codegen defect.

| `R_X86_64_GOTPCREL` and relaxable variants
| Link error in the first version.  The backend emits none.
|===

Base relocations are grouped into 4 KiB page blocks, each padded to a
multiple of four bytes.

Weak symbols from ELF objects (the runtime uses `.weak` for trampolines such
as `_BlaisePlatformInit` and for generic instances) are resolved by the
linker with the usual strong-over-weak rule; nothing weak survives into the
image.

=== Imports

A PE import names its DLL.  Three pieces deliver that:

. *Metadata section.*  A new `TContainerSectionKind` member, `cskImports`,
  mapped by the ELF writer to a non-allocated section `.blaise.imports`.  The
  assembler's `.section` handler gains one arm for it.  The section holds
  pairs of NUL-terminated strings: symbol name, library name.

. *Code generator.*  For each `external` routine the unit references, the
  backend emits one pair, taking the library from `TMethodDecl.ExternalLib`.
  This is emitted on every target — it is cheap, and the ELF and Mach-O
  linkers ignore the section — so it needs no OS test.

. *Linker.*  For every undefined symbol with a metadata entry, the linker
  maps the library name to a DLL file name through the toolkit, then builds
  the import directory, one lookup table and one address-table run per DLL, a
  hint/name entry per symbol (hint 0), and a six-byte thunk
  `jmp *IAT_slot(%rip)` that direct calls resolve to.

Library-name mapping is a toolkit method.  Initial table:

[cols="1,2",options="header"]
|===
| Bare name | DLL

| `c`, `m`
| `msvcrt.dll`

| `kernel32`, `user32`, `gdi32`, `advapi32`, `ws2_32`, …
| the name with `.dll` appended

| a name already ending in `.dll`
| used verbatim
|===

Rules:

* An undefined symbol with no metadata entry is a link error naming the
  symbol and advising `external '<dll>' name '…'`.
* A metadata entry for a symbol that the link *defines* is ignored.  This is
  how `pthread` stays out of the Windows import table: `runtime.thread` binds
  `external 'pthread'`, and `runtime.thread.windows` defines those symbols.
* On a *cross* link the linker cannot check that the DLL exports the symbol;
  a misspelling fails when the program is loaded.  On a *native* Windows link
  the linker reads the DLL's export directory with `blaise.pereader` and
  reports the error at link time.  This mirrors the native/cross split
  `ResolveLibNeeded` already makes for ELF sonames.

Imported *data* is not supported in the first version.

=== Determinism

`TimeDateStamp` is 0, `CheckSum` is 0, and every table (imports by DLL then
symbol, base relocations by address) is emitted in sorted order.  The
linked-binary fixpoint (`scripts/fixpoint-binary.sh --target windows-x86_64`)
must print `BINARY_FIXPOINT_OK`.

=== Map file

`--map <file>` writes one line per symbol: RVA, section, name.  With no PDB,
this is how a crash address from Windows is turned back into a routine name.
It is useful on every target and is specified here because Windows needs it
first.

=== Later: unwind data

Windows debuggers and the exception dispatcher walk the stack through
`.pdata` / `.xdata`.  Without them, a debugger shows no call stack through
Blaise frames.  Blaise frames are uniformly `RBP`-based, so one `UNWIND_INFO`
shape (push `RBP`, set frame register) covers almost every routine.  This is
milestone M7; nothing earlier depends on it.

== Driver and command line

* *Toolkit.*  `TWindowsX86_64Toolkit` returns `TX86_64Backend` constructed
  with `TWin64BoundaryAbi` and `TPeTlsModel`, and `nil` from
  `MakeLinkTarget`.  One `Register` call in `EnsureRegistry`.

* *Routing.*  `LinkViaInternalLinker` currently treats a `nil` link target as
  Mach-O.  The toolkit gains a method that performs (or names) the image
  link, so the driver dispatches without testing the OS.  The macOS toolkit
  is converted to the same method in M0.

* *Object versus image format.*  `TargetUsesElf` is replaced by two
  predicates, `TargetObjectIsElf` and `TargetImageIsElf`.  Each existing
  caller is reviewed and assigned to one.  `AssembleForTarget` keys on CPU and
  needs no change.  `SupportsLibrary` keys on the image format.

* *Options.*
** `--target windows-x86_64` (already parsed).
** `--subsystem console|gui`, default `console`; an error for non-Windows
   targets.  This option is the only way to select the subsystem.  A source
   directive in the style of Delphi's `{$APPTYPE GUI}` is deliberately not
   provided: the subsystem is a property of the build, not of the source, and
   such a directive would be silently ignored on every other target.
** `--map <file>`.
** `--static` is rejected, as on macOS: a PE image always binds system DLLs.
   `--dynamic` and the default behave identically.
** `--assembler external` / `--linker external` are rejected (D2).

* *Output name.*  When `--output` has no extension and the target is Windows,
  `.exe` is appended, using the existing `ExecutableExtension`.

* *RTL unit suffix.*  `RTLOSSuffix(osWindows)` returns `windows`.

* *Library search.*  `BuildLibSearchDirs` and `LinkLibSoname` move behind
  toolkit methods (M0).  The Windows toolkit's search list is the Windows
  system directory on a native host and empty on a cross host.

=== `runtime.start.windows`

`_start` is the PE entry point.  The loader enters it with the Win64
convention and no arguments.

. Establish stack alignment.
. Set the console input and output code pages to UTF-8.
. Install a vectored exception handler (see below).
. Obtain the command line with `GetCommandLineW`, split it by the standard
  Windows quoting rules, convert each argument to UTF-8, and build `argc` /
  `argv`.
. Call `main(argc, argv)`.
. Run the at-exit list and call `ExitProcess` with `main`'s result.

The vectored handler reports an access violation, stack overflow or illegal
instruction on standard error in the same style as other fatal runtime errors
and terminates the process with the exception code as its exit code (<<d7>>).
It runs before any frame-based dispatch, so it needs no `.pdata`.  For a stack
overflow it runs on what little stack remains, so it must stay small and call
nothing that allocates.  Converting faults into Blaise exceptions is a
possible later refinement and is not designed here.

[NOTE]
====
Some e2e tests assert the POSIX convention of exit code 139 for a crash.  They
move to the harness's per-target fault exit code (<<d7>>) in M3.
====

=== `runtime.syscall.windows`

Exports, by the names the core runtime already binds:

[cols="2,4",options="header"]
|===
| Symbol | Implementation

| `write`
| `WriteFile` on the handle for the descriptor

| `mmap` (anonymous only)
| `VirtualAlloc(MEM_RESERVE or MEM_COMMIT, PAGE_READWRITE)`

| `munmap`
| `VirtualFree(MEM_RELEASE)`.  `runtime.mem` only ever unmaps whole
  mappings, which is what `MEM_RELEASE` requires.

| `exit`, `_exit`, `abort`
| `ExitProcess`; `abort` writes a diagnostic first

| `__cxa_atexit`
| A Pascal at-exit list, as in `runtime.libc2.linux`

| `sysconf`
| Processor count from `GetSystemInfo`

| `_MapAnonFlag`
| A constant; the Windows `mmap` ignores the flag
|===

File descriptors.  The `TRtlPlatform` port and the stream units use small
integers.  The leaf keeps a lock-protected table from descriptor to `HANDLE`;
0, 1 and 2 are pre-bound to the standard handles.  Code that tests `Fd >= 0`
continues to work.

These leaves are Pascal routines with the *internal* convention; only their
calls into `kernel32` cross the boundary.

=== `runtime.thread.windows`

`runtime.thread` binds these symbols through `external 'pthread'`, so by
<<d6>> its call sites use the C convention.  Every definition in this unit is
therefore declared `cdecl`, and the start-routine parameter type in
`runtime.thread` gains `cdecl` as well.  That is also the correct declaration
on POSIX targets, where the real `pthread_create` calls the start routine with
the C convention.

|===
| Symbol | Implementation

| `pthread_create`
| `CreateThread` with a C-convention trampoline that calls the Blaise start

| `pthread_join`
| `WaitForSingleObject` + `CloseHandle`

| `pthread_mutex_init` / `lock` / `unlock` / `destroy`

| `_BlaiseThreadAtExit`

=== Direct libc bindings in the compiler

The compiler binds a few libc symbols directly rather than through the
platform port — for example `getpid` and `rmdir` in
`blaise.codegen.driver.pas` and `memcpy` in `blaise.container.writer.pas`.
`memcpy` is satisfied by `runtime.cstub`.  The others either gain a leaf in
`runtime.syscall.windows` or, preferably, are routed through `GRtlPlatform`.
A full inventory is an M6 task: link `blaise.exe`, read the list of
unresolved symbols, and resolve each one deliberately.

[#testing]
== Testing

=== Layer 0 — structural, on any host

Runs in the ordinary suite; needs no Windows.

* *PE writer.*  Unit tests link small programs for `windows-x86_64` and parse
  the result with `blaise.pereader`: machine type, entry point inside
  `.text`, section flags, import directory naming the expected DLL and
  symbols, a base relocation for every absolute pointer, TLS directory
  present exactly when the program has threadvars.
* *Boundary lowering.*  `cp.test.*` assembly assertions, on a new
  `TargetWindowsX86_64`, for: integer and float argument registers, shadow
  space, by-reference aggregates, hidden-pointer returns, stack probes, the
  TLS access sequence, and foreign-entry prologues.
* *Structural cross-check.*  `scripts/windows-crosscheck-build.sh` builds the
  fixtures in `compiler/src/it/windows/` and sanity-checks each image,
  printing `WINDOWS_CROSSBUILD_OK`.
* *Independent oracle (optional).*  `llvm-readobj --file-headers --sections
  --coff-imports --coff-basereloc --coff-tls-directory` reads the same images
  with a parser Blaise did not write.

=== Layer 1 — behavioural, local VM

`scripts/windows-vm.sh`, modelled on `scripts/freebsd-vm.sh`.  It drives the
UTM virtual machine by name through `utmctl`, and reaches the guest over SSH.
`stdlib-test` and `selfhost` are added by the milestones that make them
possible (M3 and M7).

[cols="2,4",options="header"]
|===
| Command | Effect

| `start` / `stop` / `status`
| Start the VM and wait for SSH; shut Windows down, powering off only if it
  hangs; report

| `ssh [cmd]`
| Shell or one `cmd.exe` command in the guest

| `run <exe> [args]`
| Copy an executable into a per-run directory under `C:\blaise-test`, run it,
  remove the directory, exit with its exit code

| `crosscheck`
| Build the `compiler/src/it/windows/` fixtures and check their output and
  exit codes; prints `WINDOWS_CROSSCHECK_OK`

| `stdlib-test [args]`
| Cross-build the stdlib TestRunner and run it in the guest

| `selfhost`
| Cross-build `blaise.exe`, have it rebuild itself in the guest, and compare
  the two images byte for byte
|===

Like the FreeBSD script it builds from the working tree with
`compiler/target/blaise`.  Unlike it, there is no `setup` that installs the
OS unattended; the guest is installed once by hand (<<host-setup>>).

The guest is Windows 11 ARM64.  It runs the x64 images through emulation.

[WARNING]
====
Emulated x64 is not real x64.  The loader, the system DLLs and the ABI are
genuine, so this lane validates the PE image, imports, TLS, the boundary ABI
and the runtime.  It does *not* validate CPU-feature-dependent paths —
notably the AVX2 routines in `runtime.utf8` — or timing-sensitive behaviour.
Layer 2 covers those.
====

=== Layer 2 — real x64, in CI

A `windows-crosscheck` job in `.github/workflows/bootstrap.yml`:

. on the Linux runner, cross-build the fixtures, the stdlib TestRunner and
  `blaise.exe`, and upload them;
. on `windows-latest`, download and run them; then run the self-host check.

It follows the validate-on-a-temporary-branch rule like every other job.

=== Layer 3 — foreign-function fixtures

A small C DLL, built with mingw-w64, exports routines covering every boundary
case: mixed integer/float arguments beyond four, aggregates of 1–16 bytes by
value, aggregate returns of each size class, a variadic routine, and routines
that call back into Blaise.  The Blaise side asserts round-tripped values.
This is the only test that proves the Win64 lowering against an independent
compiler.

The types × constructs rule applies: every integer kind, enum and Boolean,
at boundary values, through the foreign call path.

=== Self-hosting gate

The target is complete for the compiler when the cross-built `blaise.exe`
rebuilds itself on Windows and the result is byte-identical to the cross-built
one — the same criterion the release process applies to the Linux binary.

[#host-setup]
== Development-host setup

The guest is installed once by hand.  The steps below are the ones used to
build the `blaise-win11` guest on 2026-11-11; `scripts/windows-vm.sh` assumes
the names, port and key they produce, each of which can be overridden through
the environment variables listed in the script's header.

A fresh ARM64 install is required: the existing VirtualBox machines are x64
and would run under full emulation.  Plan for about 25 GB of disk once
Windows is installed and updated.

=== Host software

[source,sh]
----
brew install --cask utm
brew install --cask crystalfetch      # only if Microsoft's ISO page offers none
brew install mingw-w64 llvm           # optional: Layer 3 fixtures, PE oracle
----

=== Installation image

Download the Windows 11 Arm64 ISO from Microsoft's
`software-download/windows11arm64` page.  When that page offers no ISO,
CrystalFetch builds one from Microsoft's update servers.  No licence key is
needed: an unactivated installation runs indefinitely with a watermark.

=== Creating the VM in UTM

. *+* → *Virtualize* → *Windows*.  Keep *Install Windows 10 or higher* and
  *Install drivers and SPICE tools* ticked, and choose the ISO as the boot
  image.
. 8192 MB of memory, 4 CPU cores, a 64 GB disk.  The disk image is sparse and
  grows only as Windows writes to it.
. Name the VM `blaise-win11` and save it, without starting it.
. _Optional, when the Mac is short of space:_ move the VM to another volume
  before the first start.  Either use *Move…* from the VM's context menu, or
  quit UTM, move the `blaise-win11.utm` bundle out of
  `~/Library/Containers/com.utmapp.UTM/Data/Documents/` and reopen it with
  *File → Open…*.  An NFS share works; allow UTM access to network volumes
  when macOS asks.  Keep the share mounted while the VM runs.  Should QEMU
  report that it cannot lock the disk image, mount the share with the
  `locallocks` option.
. *Settings → Network:* set *Network Mode* to *Emulated VLAN* and add a port
  forward: TCP, guest port 22, host address `127.0.0.1`, host port 2222, guest
  address left blank.  The forward listens on the loopback address only, so
  the guest is unreachable from the network.

=== Installing Windows

. Start the VM and press a key at "Press any key to boot from CD or DVD".
. Choose Windows 11 Pro and a custom install onto the empty disk.
. Out-of-box setup insists on a Microsoft account.  Press *Shift+F10* and run
  `start ms-cxh:localonly`; on builds where that does nothing, run
  `OOBE\BYPASSNRO`, after which setup offers "I don't have internet".  Create
  the local account `blaise`.
. Once logged in, run the UTM guest tools installer from the driver CD and
  reboot.  It installs the network and display drivers.  *Do not select the
  experimental 3D graphics driver*: it needs the `virtio-gpu-gl-pci` display
  card, and with any other card the display stays black with "Display output
  is not active".  The VM's display card should be `virtio-ramfb` or
  `virtio-gpu-pci`.

=== Configuring the guest

In an administrator PowerShell:

[source,powershell]
----
# OpenSSH server, started now and at every boot
Add-WindowsCapability -Online -Name OpenSSH.Server~~~~0.0.1.0
Start-Service sshd
Set-Service sshd -StartupType Automatic

# The capability's own firewall rule did not admit forwarded connections
# (ssh from the host timed out "during banner exchange"); a port rule does.
New-NetFirewallRule -DisplayName 'SSH 22 in' -Direction Inbound -Protocol TCP -LocalPort 22 -Action Allow -Profile Any

# A crashing test exits instead of waiting for a click
New-Item -Force 'HKLM:\SOFTWARE\Microsoft\Windows\Windows Error Reporting' | Out-Null
Set-ItemProperty 'HKLM:\SOFTWARE\Microsoft\Windows\Windows Error Reporting' -Name DontShowUI -Value 1 -Type DWord
Set-ItemProperty 'HKLM:\SOFTWARE\Microsoft\Windows\Windows Error Reporting' -Name Disabled -Value 1 -Type DWord

# The test directory, excluded from Defender real-time scanning, which
# otherwise delays every freshly copied executable
New-Item -ItemType Directory -Force C:\blaise-test | Out-Null
Add-MpPreference -ExclusionPath C:\blaise-test

# Never sleep
powercfg /change standby-timeout-ac 0
powercfg /change monitor-timeout-ac 0
----

No x64 emulation package is needed: Windows 11 on ARM runs x64 executables
out of the box.

=== The SSH key

On the host:

[source,sh]
----
ssh-keygen -t ed25519 -f ~/.ssh/blaise_windows -N ""
scp -P 2222 ~/.ssh/blaise_windows.pub blaise@127.0.0.1:

keys from `C:\ProgramData\ssh\administrators_authorized_keys`, not from the
user's `.ssh` directory.  The file must be readable by Administrators and
SYSTEM only.  In the administrator PowerShell:

== Risks

[cols="2,4",options="header"]
|===
| Risk | Mitigation

| No register is reliably free for the TLS base at every threadvar access
| Establish the guarantee before converting call sites; fall back to
  save/restore inside the PE model.  Reference: the arm64 TLV path.

| The backend relies on the red zone somewhere
| M0 audit.  If found, fix generally — it is harmless on other targets.

| A stack probe is missed on a path that allocates dynamically
| Layer 0 assertion on a routine with a large frame; a guest fixture that
  recurses with large frames on a secondary thread.

| An import is misspelt and the cross link cannot tell
| Native-host export check (M7); the CI job runs every fixture, so a bad
  import fails there.

| Emulated x64 hides a real-hardware defect
| The CI lane and the Ryzen machine.

| A Blaise routine defines a symbol that is bound through a named library but
  is not declared `cdecl`
| M3 audit of the Windows leaf units against <<d6>>; the thread e2e tests
  fail immediately if `pthread_*` is wrong.

| A callback without `cdecl` is silently wrong
| It is a compile error on Windows and a warning elsewhere
  (<<abi-language-rule>>).

| The external LLVM backend emits Win64 calls between Blaise routines
| It must mark Blaise routines `x86_64_sysvcc` when targeting Windows.
  Record this in that backend's notes.

| Windows Defender or SmartScreen interferes with freshly built executables
| Guest exclusion for the test directory; note for end users in the release
  documentation.
|===

[appendix]
== What the compiler provides for a future pdr port

The debugger port is a separate project.  This appendix lists only the
compiler-side facts it will depend on, so they are settled here and not
discovered later.

* *OPDF location.*  The merged OPDF records are in a PE section named
  `.opdf`.  The records themselves are byte-identical to the ELF form.
* *Addresses.*  OPDF records carry absolute addresses computed against
  `ImageBase`.  Every such address has a base-relocation entry, so the loaded
  image contains the *slid* value.  A debugger reading the file sees unslid
  values and applies `actual base − ImageBase` itself, as pdr already does
  for PIE executables.  The linker must not mark `.opdf` discardable if pdr
  is to read it from the running process; it may if pdr reads the file.  The
  first version keeps it loadable.
* *Thread-local variables.*  A threadvar's OPDF location is an offset from
  the start of the image's TLS block.  The debugger finds the block through
  the thread environment block and `_tls_index`; the map file and the symbol
  give `_tls_index`'s address.
* *Frames.*  Routines use an `RBP` frame, so a frame-pointer walk works
  without `.pdata`.  Foreign-entry routines save extra registers below the
  frame pointer; parameter locations in OPDF must reflect the homes the body
  uses, not the Win64 arrival registers.
* *Entry breakpoints.*  The existing caveat holds: a breakpoint on a
  routine's first instruction stops before parameters reach their homes.
  For a foreign-entry routine this window is longer.
* *Process control.*  Windows offers the debug-event API (`WaitForDebugEvent`
  and friends) in place of `ptrace`.  Unlike the current Linux adapter it
  reports thread creation natively, so the thread limitation recorded for pdr
  on Linux need not carry over.
