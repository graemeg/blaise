== Motivation

=== The `Integer`/`Cardinal` lie

Pascal introduced semantic type names so code would scale across 16-, 32- and
64-bit platforms:

* `Integer` — "the natural signed integer for this platform"
* `Cardinal` — "the natural unsigned integer for this platform"

When 64-bit systems became ubiquitous in the mid-2000s, Delphi and FPC froze
both at 32 bits for backwards compatibility. The original promise of
platform-native sizing is gone; the names now suggest something they do not
deliver. On a modern 64-bit machine:

[source,pascal]
----
{ FPC/Delphi on a 64-bit system }
var x: Integer;        { 32-bit, despite the name }
var y: Cardinal;       { 32-bit, despite the name }
var z: Int64;          { 64-bit as expected }
----

Blaise documents its own `Integer` honestly as a fixed 32-bit type
(`docs/language-rationale.adoc`, integer types section), so within Blaise the
defect is one of connotation rather than of behaviour. The substantive problem
is different: Blaise has *no default integer type that matches the machine*.
Lengths, counts and indices are 32-bit, which imposes a 2^31^-element ceiling
on strings, `RawBytes` and collections in a 64-bit systems language, and every
developer arriving from Go, Swift or Rust must first learn which of several
historical names to use.

=== The floating-point mess

The classic float family has the same disease plus an architecture trap:

* `Real` — "platform-native", in practice frozen (usually 64-bit)
* `Single` / `Double` — 32-/64-bit IEEE 754 (fine, but inconsistent naming)
* `Extended` — 80-bit x87 only; code using it does not port to ARM or RISC-V
* `Comp` — an obsolete 64-bit integer in float clothing

Blaise currently provides only `Single` and `Double`; `Real`, `Extended`,
`Comp` and `Currency` were never adopted (`Currency` is dropped in favour of a
stdlib decimal type; see `docs/future-improvements.adoc`).

=== The clean-slate opportunity

Blaise carries no legacy code base and no 1980s promises. It can choose names
that are honest, consistent, and familiar to developers arriving from Go,
Swift, Rust or Zig. Critically, it chooses *new* names rather than silently
redefining old ones — redefining `Integer` to be 64-bit would be strictly
worse than dropping it, because ported code would change meaning without
changing text.

== Current state (2026-10-19)

The builtin integer and float names registered in
`TSymbolTable.RegisterBuiltins` (`compiler/src/main/pascal/uSymbolTable.pas`):

[cols="1,1,2", options="header"]
|===
| `TTypeKind` | Canonical name | Existing aliases

| `tyInteger`  | `Integer`  | —
| `tyInt64`    | `Int64`    | —
| `tyUInt32`   | `UInt32`   | `Cardinal`
| `tyUInt64`   | `UInt64`   | `QWord`, `PtrUInt`
| `tySmallInt` | `SmallInt` | `Int16`
| `tyWord`     | `Word`     | `UInt16`
| `tyByte`     | `Byte`     | —
| `tySingle`   | `Single`   | —
| `tyDouble`   | `Double`   | —
|===

Observations relevant to this design:

* There is *no signed 8-bit type kind*. `Int8` (and `ShortInt` in the
  compatibility unit) cannot be a pure alias; it requires a new `TTypeKind`.
* Missing names: `Int8`, `Int32`, `UInt8`, `Int`, `UInt`, `Float`,
  `Float32`, `Float64`.
* Every currently supported target — Linux x86-64, FreeBSD x86-64, macOS
  arm64 — is LP64. A platform-sized `Int` is therefore 64-bit everywhere
  today.
* Generic instantiation already treats aliases as one type: `TList<Int16>` and
  `TList<SmallInt>` in one program share an instance and link cleanly
  (verified 2026-10-19).
* Overload declaration does *not*: two overloads differing only by an alias are
  accepted and collide in the assembler. Tracked as
  `BUG-20261019-alias-duplicate-overload`; see <<d12>>.
* `Format('%d', [AnInt64])` formats the full 64-bit value (verified
  2026-10-19), so the Phase 0 prerequisite of the original draft is already
  met. The `%u` (unsigned decimal) specifier is not supported.
* `docs/language-rationale.adoc` currently records "platform-native integer
  width" as a *rejected* alternative. Phase 3 revises that section.

== The type families

[cols="1,2,2", options="header"]
|===
| Family | Types | Meaning

| Platform-native integer
| `Int`, `UInt`
| Pointer-width signed/unsigned integer (64-bit on every currently supported
  target; 32-bit on a future 32-bit target)

| Fixed-width integer
| `Int8`, `Int16`, `Int32`, `Int64` +
  `UInt8`, `UInt16`, `UInt32`, `UInt64`
| Exactly the stated width, on every platform, forever

| Floating point
| `Float`, `Float32`, `Float64`
| IEEE 754; see <<float-sizing>> — `Float` is a fixed alias of `Float64`,
  NOT platform-sized

| Octet
| `Byte`
| Builtin alias of `UInt8`; see D7

| Unchanged
| `Boolean`, `Char`, `String`, `Pointer`, `RawBytes`
| Not part of this standardisation
|===

Removed as builtins in Phase 6 (available afterwards only via the
compatibility unit, <<classic-unit>>):
`Integer`, `Cardinal`, `Single`, `Double`, `SmallInt`, `Word`, `QWord`,
`PtrUInt`. The compatibility unit additionally supplies names Blaise never
had as builtins: `ShortInt`, `LongInt`, `LongWord`, `NativeInt`,
`NativeUInt`, `PtrInt`, `Real`, `Extended`, `Comp`.

Design properties this buys:

* *Honesty* — `Int` genuinely adapts to the platform, and the documentation
  says so upfront.
* *Clarity in systems code* — `UInt32` or `Float64` means exactly that width,
  always, everywhere.
* *Uniform naming* — everything derives from `Int`, `UInt` or `Float`;
  the fixed-width name is the base name plus its width.
* *Portability by default* — no x86-only `Extended`; nothing in the core
  language is architecture-specific.
* *Familiarity* — `Int` as the pointer-sized default matches Go `int`, Swift
  `Int` and Rust `isize` (note the false friend in D9 for developers arriving
  from Kotlin, Java or C#).

== Design decisions

All decisions below are *decided*. Each lists the options considered, the
analysis, and the outcome.

=== D1. `Int`/`UInt` platform-native sizing — decided

*Options.*

. Platform-native (Go `int`, Swift `Int`, Rust `isize`, Zig `usize`).
. Fixed 64-bit under the name `Int` (C#'s `long`-by-another-name).
. Retain frozen-32-bit semantics under a new name.

*Analysis.* Pointer-width integers are justified by hardware reality: array
indexing, lengths, memory sizes and pointer arithmetic genuinely scale with
the platform word. Option 3 recreates the problem being solved. Option 2 is
defensible but wastes the honest name — and on a hypothetical 32-bit embedded
target it forces 64-bit arithmetic everywhere. Every currently supported
target is 64-bit, so `Int` = `Int64` in practice; the 32-bit behaviour is a
promise that stays untested until a 32-bit target exists. A future i386/arm32
port must budget a revalidation pass for code that silently assumed 64-bit
`Int`.

*Decision.* Option 1, platform-native (pointer-sized). The untested-32-bit
caveat is recorded in the language rationale.

[#float-sizing]
=== D2. `Float` sizing — decided: fixed alias of `Float64`

*Original proposal.* `Float` (announced as `Real`) is platform-sized: 32-bit
on 32-bit platforms, 64-bit on 64-bit platforms, for naming symmetry with
`Int`.

*Options.*

. Platform-sized `Float` (the original proposal).
. `Float` is a fixed alias of `Float64` on every platform.
. No `Float` at all — users must write `Float32`/`Float64`.

*Analysis.* The symmetry argument does not survive contact with hardware.
`Int` tracks the platform word because pointers, indices and sizes do. Floats
have no such coupling: a 32-bit x86 or ARM CPU has an FPU that processes
64-bit doubles natively — there is no performance, ABI or correctness reason
for a 32-bit platform to prefer 32-bit floats. No mainstream language ships a
platform-sized float (C `double`, Go `float64`, Rust `f64`, Swift `Double`
are all fixed), and the reason is semantic, not aesthetic: *integer width
differences affect range; float width differences change every intermediate
rounding.* A `Float` whose precision varies by target makes the same program
print different numbers on different platforms — numeric drift that no test
suite on the primary platform will ever catch. It also poisons constant
folding: the compiler could not fold `X / 3.0` without knowing the target's
`Float` width, and cross-compiled output would differ from host output in
ways unrelated to the target OS.

*Decision.* Option 2: `Float` is a fixed, transparent alias of `Float64`
everywhere — the universal "default float is double" convention. This keeps
the naming family (`Float`, `Float32`, `Float64`), answers the naming
consistency question raised in the discussion (`Real` breaking the
`Int`/`UInt` pattern), and discards only the trap. The asymmetry with `Int`
is deliberate: it is exactly the asymmetry the hardware has.

=== D3. Alias or distinct nominal type? — decided: transparent alias

*Question.* On x86-64, is `Int` *the same type* as `Int64`, or a distinct
type of identical width?

*Options.*

. Transparent alias: `Int` and `Int64` are two names for one type.
. Distinct nominal types of equal width, implicitly convertible.
. Distinct and explicitly convertible only.

*Prior art.* Go uses a transparent alias only for `byte`/`uint8` and
`rune`/`int32`; Go's `int` is a *distinct* type from `int64`, requiring
explicit conversion. Swift's `Int` is likewise distinct from `Int64`. The
languages whose `Int` Blaise follows therefore chose option 3, not option 1.

*Analysis.* Distinct types make an overload pair `F(Int)` / `F(Int64)` a
legal, portable pair on every target — which removes the overload-collision
concern raised in the discussion. The cost is conversion noise at every
boundary between "general" and "systems" code, and an overload resolver that
needs ranking rules when an argument converts implicitly to both (option 2),
plus extra work in the constant typer and generics instantiation. With a
transparent alias, `F(Int)` and `F(Int64)` collide on 64-bit targets but
would not collide on a 32-bit target. That asymmetry is acceptable: it can
only affect code first written on a 32-bit Blaise, which does not exist; the
collision is a compile-time error, never a silent change of meaning; and
overload sets should be written in fixed-width terms anyway. The alias model
requires the collision to be *reported correctly* at declaration, which today
it is not (<<d12>>).

*Decision.* Option 1, transparent alias, resolved at type-registration time
per target.

*Mechanics.*

* All new names except `Int8` map onto existing `TTypeKind`s (`Int32` →
  `tyInteger`, `UInt8` → `tyByte`, `Float64` → `tyDouble`, `Float32` →
  `tySingle`, `Int` → `tyInt64`, `UInt` → `tyUInt64`, ...). The internal
  enumeration keeps its constant names.
* `Int8` requires a *new* `TTypeKind` (signed 8-bit). That is the only part
  of Phase 1 with codegen impact: sign-extending loads and stores on both
  ISAs, range checks, conversions, `.bif` encoding, `EmitTypeDesc` in
  `uDebugOPDF.pas`, and the `flag-coverage` baseline.
* No OPDF specification or pdr change is required for `Int8`: the OPDF
  primitive record already carries a byte size and an `IsSigned` flag, and
  pdr's integer formatter (`pdr_typesys.pas`) already decodes a signed
  1-byte value. The emitter needs only a `SK_INTEGER`/`IsSigned = 1` case for
  the new kind.
* Diagnostics, RTTI and OPDF print the `TTypeDesc` name. Until Phase 6 those
  stay as they are (`Integer`, `SmallInt`, `Double`, ...) so existing test
  expectations do not churn; Phase 6 renames the canonical display names to
  the fixed-width spellings (`Int32`, `Int16`, `Float64`, ...).

=== D4. Literal typing and promotion — decided: context-typed

*Question.* What is the type of the literal `42`? Of `3.14`?

*Options.*

. Integer literals default to `Int`; float literals to `Float` (= `Float64`).
. Integer literals default to `Int32`, widening on demand.
. Literals are untyped-until-context (Go/Zig `comptime_int` style), defaulting
  to `Int`/`Float64` when context gives no hint.

*Current behaviour.* An unhinted integer literal is typed by magnitude
(`Integer` if it fits in 32 bits, else `Int64`, else `UInt64`), and the
semantic pass already performs hinted analysis (`AnalyseExprHinted`).

*Analysis.* Option 3 is closest to current behaviour and gives the best
ergonomics: `var B: UInt8 = 255;` works without casts, and an unhinted `42`
lands on `Int`. Option 2 recreates FPC's 32-bit default and makes `Int`
second-class in its own language. With `Float` fixed at 64-bit (D2), float
literal folding is target-independent. Because Blaise has no inline `var`
and no variable type inference, the blast radius of the default is smaller
than in Go or Swift: it is visible mainly in overload resolution
(`F(Integer)` vs `F(Int64)` called with `42`), generic argument inference, and
the width of intermediate arithmetic (`1 shl 40`).

*Decision.* Option 3: context-typed literals with `Int` / `Float64` defaults.

*Placement.* Changing the unhinted default from 32-bit to `Int` alters
overload selection and intermediate-arithmetic width for existing code, so it
is a breaking change and lands in Phase 4, together with D5. Phases 0–3 keep
the current magnitude rule.

=== D5. Standard function and collection signatures — decided: widen everything

*Question.* What do `Length`, `Pos`, `IndexOf`, `Count`, `SizeOf`, `Ord`,
`High`/`Low` return, and what does `SetLength` accept?

This is the largest hidden cost in the whole proposal and drives most of the
timeline. Today these traffic in 32-bit `Integer`. With `Int` as the
language's default, they return `Int` — on current targets a widening from 32
to 64 bits that ripples through every arithmetic expression, every `for` loop
bound, and every stored index field (`Integer` occurs roughly 5,600 times
across the compiler and stdlib sources).

*Consequences to plan for:*

* `TList<T>.FCount` and friends widening from 32 to 64 bits is a *field
  layout change*: the full layout-change protocol applies (stage-2 rebuild
  before trusting anything; refresh the `-pre` binary; `.bif` interface
  version bump; OPDF field-offset records; `bif-coverage --reset`).
* `for I := 0 to Length(S) - 1` — the loop variable's inferred type must
  follow, or every such loop gains a hidden narrowing.
* Code relying on 32-bit wraparound (hash functions in particular) must
  keep explicit `UInt32`/`Int32` operands; the Phase 5 rename preserves
  this, but any code that is *widened* instead of renamed must be audited.
* `MaxInt` is a 32-bit builtin constant used as a "to end of string" sentinel
  in `Copy`; it must be reviewed alongside the `Copy` count parameter.
* `Format('%d')` already handles 64-bit arguments; adding the `%u` (unsigned
  decimal) specifier is a worthwhile companion change, so that `UInt` and
  `UInt64` values above `High(Int64)` format correctly.

*Options.*

. Widen the full surface (`Length`, `Count`, `SetLength`, `IndexOf`, ...) to
  `Int` in one coordinated change.
. Keep 32-bit returns under the new spelling `Int32` and defer widening.
. Widen `Length`/`SetLength` (language builtins) but keep collection `Count`
  at `Int32`.

*Analysis.* Option 3 creates a permanently inconsistent surface — the worst
outcome. Option 2 is honest but bakes a 2-billion-element ceiling into a
64-bit systems language and guarantees a second migration later, when there
will be more code and more external users. Option 1 costs one coordinated,
well-understood layout-change cycle now, while the user base is small.

*Decision.* Option 1, as its own phase (Phase 4) with the full verification
battery, at the start of the v0.16 cycle.

=== D6. Steering users away from `UInt` for counting

`for I := Count - 1 downto 0` with an unsigned index underflows at zero and
never terminates — the classic unsigned-loop trap, and the reason Go made
`len()` signed. `Length`/`Count` therefore return *signed* `Int`, and the
documentation states plainly: use `Int` for counting and indexing; reserve
`UInt`/`UIntNN` for bit manipulation, hashes, and formats that are defined as
unsigned. A semantic warning on `downto 0` over an unsigned loop variable is
a cheap diagnostic added in Phase 4.

=== D7. Which classic names survive as builtins? — decided: `Byte` only

*Analysis.* `Byte` is semantic rather than legacy — "one raw octet" versus
"a small number". Go kept `byte` as an alias of `uint8` for exactly this
reason, Blaise's `RawBytes`-centric binary I/O reads naturally with it, and
the discussion asked for it to stay. Everything else in the classic family
(`Word`, `SmallInt`, `ShortInt`, `LongInt`, `Cardinal`, `Integer`, `Single`,
`Double`, `Real`) carries FPC's frozen-width connotations and belongs in the
compatibility unit only.

*Decision.* `Byte` remains a builtin, as a transparent alias of `UInt8`
(`UInt8` becomes the canonical display name in Phase 6). `Char` is unrelated
to this proposal and stays.

[#classic-unit]
=== D8. The `ClassicPascalTypes` compatibility unit

An opt-in stdlib unit restoring the familiar names as transparent aliases,
for porting FPC/Delphi code. (The announcement called it
`LegacyPascalTypes`; `ClassicPascalTypes` was chosen as the friendlier name.)

[cols="1,1,2", options="header"]
|===
| Classic name | Maps to | Note

| `Integer`     | `Int32`   | Frozen width preserved — ported code keeps its semantics
| `Cardinal`    | `UInt32`  |
| `SmallInt`    | `Int16`   |
| `ShortInt`    | `Int8`    | Requires the new signed 8-bit kind (D3)
| `Word`        | `UInt16`  |
| `LongInt`     | `Int32`   |
| `LongWord`    | `UInt32`  |
| `QWord`       | `UInt64`  |
| `NativeInt`   | `Int`     |
| `NativeUInt`  | `UInt`    |
| `PtrInt`      | `Int`     |
| `PtrUInt`     | `UInt`    |
| `Single`      | `Float32` |
| `Double`      | `Float64` |
| `Real`        | `Float64` |
| `Extended`    | `Float64` | Precision CHANGE versus x86 FPC: 80-bit results become 64-bit — documented prominently
| `Comp`        | `Int64`   | It always was one
|===

Key points:

* The mapping is deliberately *frozen-width* (`Integer` → `Int32`, not
  `Int`): ported code keeps the semantics it was written against.
* `Extended` → `Float64` silently changes results for code that genuinely
  exploited 80-bit intermediates. The unit's documentation carries a warning,
  and the migration analyser flags every `Extended` use site.
* `Int64`/`UInt64` need no entry — the names are already canonical.
* Mechanically the unit is exported type aliases.  A unit cannot redeclare
  a builtin type name (`Duplicate type name 'Integer'`; verified in Phase 2),
  so the unit is delivered in two steps.  Phase 2 ships the names Blaise has
  no builtin for: `ShortInt`, `LongInt`, `LongWord`, `NativeInt`,
  `NativeUInt`, `PtrInt`, `Real`, `Extended`, `Comp`.  The eight classic
  names that are still builtins (`Integer`, `Cardinal`, `SmallInt`, `Word`,
  `QWord`, `PtrUInt`, `Single`, `Double`) move into the unit in Phase 6, in
  the same commit that removes them as builtins.  Code that uses the unit
  sees the full classic set at every point in between.
* Pointer aliases follow their base names.  `System` provides `P` + each
  builtin name (`PInt32`, `PUInt8`, `PInt`, `PFloat64`, ... and, while those
  names are builtins, `PInteger`, `PCardinal`, `PSmallInt`, `PWord`, `PQWord`,
  `PPtrUInt`, `PSingle`, `PDouble`); the unit provides the pointer aliases of
  its own names (`PLongInt`, `PShortInt`, `PReal`, ...).  Each is the same type
  as its `^Base` form.  The classic `System` pointer aliases move into the unit
  in Phase 6, with their base names.

=== D9. The C interop false-friend

For the fixed-width family, C interop is self-describing (`Int32` ↔
`int32_t`). The trap is the short name: on LP64 targets, C `int` is 32-bit but
Blaise `Int` is 64-bit. Go users hit the equivalent trap constantly, and
developers arriving from Kotlin, Java or C# — where `Int`/`int` is a fixed
32-bit type — meet the same false friend. The interop documentation states
the rule in one line — *when transcribing a C header, C `int` is `Int32`, C
`long` on LP64 is `Int64`, and Blaise `Int` corresponds to C
`intptr_t`/`ssize_t`, never to C `int`* — and `bindgen` output follows that
mapping.

=== D10. Compiler-internal usage

The compiler, runtime and stdlib use the fixed-width names. The
behaviour-preserving migration is the *mechanical rename* `Integer` → `Int32`,
`Cardinal` → `UInt32`, `Double` → `Float64` etc., which changes no layout, no
semantics and no generated code — an ideal fixpoint-verified commit.
Opportunistic *widening* of internal fields to `Int` is a separate,
case-by-case decision outside the rename (widening a field is a layout
change; see D5). The internal `TTypeKind` enumeration keeps its existing
constant names — renaming `tyInteger` across the source tree buys nothing and
risks much.

=== D11. Removal without a deprecation period — decided

*Options.*

. The old builtin names emit a deprecation warning for one release, then are
  removed.
. Hard removal in Phase 6, with a targeted error message.

*Analysis.* Blaise is at an early stage; its users expect breaking change
between releases, and a warning cycle would delay the flip by a full release
for little benefit. Guidance is better delivered by tooling than by the
compiler: BlaiseGuard already performs source analysis and can report every
classic type name together with its recommended replacement.

*Decision.* Option 2. The compiler emits no deprecation warnings. After
Phase 6 an unknown classic name produces an error that names the fix
("`Integer` is not a builtin type — use `Int32` (or `Int`), or add
`uses ClassicPascalTypes`"). A new BlaiseGuard rule, introduced in Phase 2,
reports classic type names with the recommended migration (`Integer` →
`Int32`, or `Int` for counts and indices; `Double` → `Float64`; `Extended` →
`Float64` with a precision warning; ...).

[#d12]
=== D12. Alias-identical overloads are a declaration error — decided

*Problem.* Two `overload` routines whose parameter types differ only by an
alias (`UInt32`/`Cardinal`, `Int16`/`SmallInt`) are accepted today. With no
call site the build fails in the internal assembler (`duplicate label:
_F_D_u`); with a call site the error is "Ambiguous overload" at the call
rather than at the declaration (`BUG-20261019-alias-duplicate-overload`).
This design adds several new alias pairs (`Int`/`Int64`, `Byte`/`UInt8`,
`Float`/`Float64`, `Int32`/`Integer`), which would make the defect common.

*Decision.* Overload signatures are compared by resolved type identity, and a
duplicate is rejected at the second declaration with a message that names
the alias relationship, for example: "Overload of 'F' has the same signature
as the declaration at line 2 (`Int` and `Int64` are the same type on this
target)". This is fixed first, in Phase 0.

== Revisions to the original announcement

The announcement in discussion #106 is revised on the following points:

. *Platform-sized `Real`* — replaced by `Float`, a fixed alias of `Float64`
  (D2).
. *`LegacyPascalTypes`* — renamed `ClassicPascalTypes` (D8).
. *`Byte`* — stays as a builtin alias of `UInt8` (D7), following community
  feedback.
. *"Rolling out over the next few days"* — the self-hosting chain makes that
  unrealistic for the full migration. Every new type name must be *taught* to
  the compiler in one commit before any later commit may *use* it (the
  teach-then-use rule the rolling bootstrap enforces), the stdlib widening is
  a field-layout change requiring the full stage-2 and fixpoint discipline,
  and the final removal of the old builtins touches every test source. The
  realistic shape is: additive half in v0.15.0, breaking half at the start of
  the v0.16 cycle, where it gets CI soak time before the next release.

[#timeline]
== Implementation timeline

Ordered for the self-hosting chain: each phase is one or more commits, each
commit passes the full verification battery (the five fixpoint scripts plus
the full test suite built by the stage-2 compiler, on Linux x86-64 and macOS
arm64), and no commit uses a name the previous commit's binary does not know.
Every new language-visible name gets a semantic unit test and an e2e test, per
the project's test rules.

=== v0.15.0 — additive, nothing breaks

*Phase 0 — prerequisites.*

* Fix `BUG-20261019-alias-duplicate-overload` (D12): reject alias-identical
  overload signatures at declaration.

== Phase 4 implementation plan

Status: ACCEPTED 2026-10-27.  The open questions were resolved the same

=== Findings that shape the plan

The following were established against master `9b709994` while preparing
this plan.

[cols="1,3",options="header"]
|===
| Area | Finding

| Implicit narrowing
| Assigning or passing a wider integer to a narrower one is accepted
  silently and truncates (`I := L`).  Widening a builtin's return type is
  therefore source-compatible: no existing call site stops compiling.  The
  parameter route did not truncate on arm64
  (`BUG-20261027-int64-arg-to-integer-param-not-narrowed`, fixed before
  Phase 4 starts); after the fix both routes agree.

| Intermediate width
| Neither backend wraps an overflowing `Integer` expression consistently
  (`BUG-20261027-int32-overflow-not-wrapped`).  With `I = High(Integer)`,
  `(I + 1) div 2` is `1073741824` on both ISAs, and `WriteLn(I + 1)` prints
  `-2147483648` on x86-64 but `2147483648` on arm64; `I + 1 < 0` is `True`
  on both.  The expression is typed `Integer`, but the 64-bit register
  value reaches some consumers unnarrowed.  Phase 4 changes which
  expressions are 32-bit, so this has to be settled first (see 4.0).

| Literal typing
| Two sites implement the magnitude rule: `AnalyseExpr` for a
  `TIntLiteral` (`uSemantic.pas`, ~19274) and the untyped-constant typer
  (~7997).  A literal next to a typed operand already takes that operand's
  type.  (Since 4.0 the *operation* `I + 1` is promoted to `Int64`; see
  below.)  `F(42)` against an `F(Integer)`/`F(Int64)` overload pair is
  reported as ambiguous today.

| Builtin results
| `Length`, `Pos`, `PosEx`, `SizeOf`, `Ord`, and `High`/`Low` of strings and
  arrays return `FTable.TypeInteger`.  `Copy` and `SetLength` check their
  count arguments with `AnalyseIntegerArg`.  `MaxInt` is a 32-bit builtin
  constant.

| Storage
| The string header is 12 bytes: three 4-byte fields, RefCount, Length and
  Capacity (`runtime.str.pas`, `HDR_SIZE = 12`).  The dynamic-array length is
  a 4-byte field at offset -4.  Widening the *type* `Length` returns does not
  lift the 2^31^ ceiling; only widening these headers does.

| Collections
| `generics.collections` holds `FCount`/`FCapacity: Integer` in at least six
  classes; `Classes.TStringList` likewise.  Widening them changes field
  layout.
|===

=== Literal typing rule (D4, made precise)

"Context-typed" is adopted in the Go sense, which keeps the blast radius
small:

. A literal with a type hint (assignment target, parameter, typed constant,
  array index, case label) takes the hinted type when the value fits.  This
  is today's behaviour.
. A literal that is one operand of a binary operator whose other operand has
  an integer type takes that type when the value fits.  (Before 4.3 this
  held only because both were `Integer`; 4.3 implements it, shifts
  excepted.)  The literal's type is then irrelevant to
  the result: since 4.0, arithmetic on two operands narrower than 64 bits
  is evaluated in `Int64` (see "Integer Expression Width" in the language
  rationale).
. Otherwise the literal is `Int` (the only change), or `UInt64` above
  `High(Int64)`.  An untyped constant (`const N = 42;`) follows the same
  default.

What changes in practice is limited to fully unhinted positions:
`F(42)` against `F(Int32)`/`F(Int64)` resolves to `F(Int64)` instead of
being ambiguous; `1 shl 40` is unchanged (already `Int64` by magnitude) but
`1 shl 31` becomes positive; `WriteLn(42)` routes through the 64-bit
writer.  (Generic arguments are not inferred from call arguments, so the
default has no effect there yet.)
(`Format('%d', [42])` does not: see step 4.3.)

=== Commit sequence

Each step is one or more commits, each fully verified (the five fixpoints
and the full suite built by stage-2, on macOS arm64 and the Linux x86-64
VM), and each lands on master through a `ci/**` branch.

*4.0 — prerequisites.*  Both done on 2026-10-27.

* Fix `BUG-20261027-warm-rebuild-arm64-backend-fieldcleanup`: Phase 4 work
  is a long run of incremental rebuilds, and editing the arm64 backend
  currently breaks a warm build.  Add an edit-one-unit leg to
  `fixpoint-warmcache.sh`.
* Fix `BUG-20261027-int32-overflow-not-wrapped`.  This needed a language
  decision, taken after comparing FPC, Delphi, Java, Rust, Swift and Go:
  arithmetic (`+ - * div mod`, unary minus, `and or xor`) on operands
  narrower than 64 bits is promoted to `Int64` (the FPC rule); shifts
  promote 8/16-bit operands to 32 bits and otherwise keep their width; `not`
  keeps its operand's type.  Recorded in the language rationale, "Integer
  Expression Width".  Tests: `cp.test.intwidth`, `cp.test.e2e.intwidth`.

*4.1 — D6 diagnostic (non-breaking).*  A warning for `downto` with an
unsigned loop variable and a lower bound of 0.  Independent of everything
else; lands first to give it soak time.  Done 2026-10-27: the warning fires
for a `Byte`, `Word`, `UInt32` or `UInt64` counter, `downto` a constant 0,
from a start that is not a constant (a constant start is never negative).
Since GH #237 such a loop ends correctly at 0; the trap is a start of
`Count - 1` with `Count = 0`, which wraps to `High(T)`.  Tests in
`cp.test.forloop`.

*4.2 — `Format('%u')`.*  The unsigned decimal specifier, so `UInt`/`UInt64`
values above `High(Int64)` format correctly.  Done 2026-10-27, in
`runtime.str` (the Format RTL is part of the compiler's RTL, not the
stdlib), with an e2e test in `cp.test.e2e.typestd`.  `%u` reads the 64-bit
argument as unsigned: the argument record does not carry the original
width, so a negative `Integer` prints its 64-bit two's complement where
Delphi prints the 32-bit one.

*4.3 — literal default (D4).*  Change the unhinted default from `Integer` to
`Int` at both typing sites.  Before committing, measure the effect on the
compiler's own code by diffing the stage-2 assembly against the previous
stage-2: every changed function is an unhinted literal whose width changed,
and each needs a look.  Expected test churn: assertions on the resolved type
of a bare literal, and overload-ambiguity tests that now resolve.

Done 2026-10-29.  Rules 1 and 2 of the literal typing rule turned out not to
be implemented as rules: they held only because a literal and an `Integer`
operand had the same type.  4.3 implements them (see "Integer literal
typing" in the language rationale for the user-facing statement):

* Rule 1 (hint): a simple constant (literal, negated literal, constant
  identifier) is retyped to the hinted integer type when it fits, at every
  value site (assignment, argument, `for` bound, `case` label, default
  parameter, element store).  A constant expression keeps `Int` and is
  narrowed on store.
* Rule 2 (typed operand): in a binary operator other than a shift or `in`,
  a simple constant takes the other integer operand's type when it fits.
  Without it, `I = 5` became a 64-bit compare of a 32-bit value, and the
  arm64 backend relies on `w` compares for 32-bit ordinals (their upper
  halves are non-canonical).
* Decided with the step: a non-negative constant converts implicitly to
  `UInt64` (assignment, argument, operand).  Otherwise `U := 1` and the
  RTL's `V and (LT_BUCKETS - 1)` needed a cast; a non-constant `Int64` still
  does.
* Overloads: a constant scores as an exact match for every integer formal
  that holds it, ranked by distance from its own type (signed first); a
  formal too narrow for it is no match.  A bracket literal ranks element by
  element.
* `array of const`: an integer constant that fits 32 bits is still passed
  as `vtInteger`, as in FPC and Delphi.  This revises the plan's
  expectation that `Format('%d', [42])` would take the 64-bit path: code
  that handles `vtInteger` alone (the test suite had three such programs)
  would otherwise lose every literal argument.

Found on the way and fixed first (`7e3cc4c7`): x86-64 took a comparison's
width from its left operand, so `Integer < Int64` compared 32 bits, and
arm64 compared a narrow operand with a 64-bit one without re-extending it;
`Ord` of a `UInt32`, `Int64` or `UInt64` was typed `Integer`.

Measured effect on the compiler's own code (stage-2 assembly of the
compiler, before and after): arm64, 114 of 10,064 functions changed, x86-64
31 of 9,530.  Almost every change removes a sign extension of a literal
compared with an `Int64`; the rest are `not` of a literal computed in 64
bits, `IntToStr` of a constant expression routed to `Int64ToStr`, and one
`Length(...) < 32 * 16` that is now a 64-bit compare.  No computed value
changed.  Test churn: assertions on the type of a literal or constant
expression (nine) and the overload tests that now resolve.

*4.4 — builtin results (D5, part 1).*  `Length`, `Pos`, `PosEx`, `SizeOf`,
`Ord`, and `High`/`Low` of strings and arrays return `Int`; `Copy` and
`SetLength` accept `Int`.  Storage is still 32-bit at this step, so
`SetLength` and the string allocators reject a length above `High(Int32)`
with a run-time error rather than truncating; 4.5 removes that limit.  No
layout change.  Audit wraparound-dependent code (hash functions in
particular) for `shr`, `div`, `mod` and comparisons whose operand silently
widens; `+`, `-` and `*` produce the same low 32 bits either way.

Done 2026-10-29.  The semantic change is the result types; the work was in
what had relied on them being 32-bit:

* Results.  `Length`, `Pos`, `PosEx`, `SizeOf`, `Ord` and `High`/`Low` of
  a string or array are `Int`.  The ordinal forms `High(T)`/`Low(T)` keep
  their argument's type, and `Ord` of a `UInt64` keeps `UInt64`, whose
  values do not all fit in `Int`.
* Extension.  A result typed `Int` must be a canonical 64-bit value.
  x86-64 already sign-extended `Length` and `Pos`, but not `PosEx`, so
  `PosEx`'s `-1` read as 4294967295; arm64 extended neither `Pos`, `PosEx`
  nor the dynamic-array `Length`.  `Ord` passed its argument through
  unextended on both; it now extends from the argument's width (an enum
  sign-extends, since an explicit ordinal may be negative).
* Counts.  `_StringCopy`, `_StringDelete`, `_StringPosEx`,
  `_StringSetLength` and `_DynArraySetLength(M)` take `Int64` counts, and
  both backends pass the count extended from its own width; before, x86-64
  passed the low 32 bits, so `Copy(S, 1, (1 shl 32) + 2)` copied two
  characters.  `Delete` was added to the step: it takes the same "to the
  end" count as `Copy`, which 4.7 makes 64-bit.  `SetLength` and the string
  allocator abort with "Runtime error: ... length above High(Int32)"
  until 4.5 widens the headers.
* Decided with the step: an `Int` that is non-negative by construction
  (`Length`, `SizeOf`, `Ord` of an unsigned ordinal, a character or an
  enum with no negative ordinal) converts implicitly to `UInt64`, in
  assignment, argument, arithmetic, bitwise and comparison operands, as a
  non-negative constant does.  Otherwise every `UInt64` hash over `Ord(C)`
  needed a cast: these results were `Integer`, which widens into `UInt64`.
  `Pos`, `PosEx`, `High` and expressions built from these results still
  need the cast.

Wraparound audit, by the same measurement as 4.3 (stage-2 assembly of the
compiler before and after): arm64, 275 of 10,068 functions changed,
x86-64 306 of 9,534.  Every change falls in one of a few classes: an
`Integer` compared with an `Int` result is extended and compared in 64
bits; two `Int` results compare in 64 bits; the added result extensions
above; counts passed in 64 bits; an extension no longer needed where an
`Int64` meets a result that used to be `Integer`; `IntToStr` of an `Int`
result routed to `Int64ToStr`.  There is no `shr`, `div` or `mod` change:
since 4.0 the arithmetic around these results was already 64-bit.  No
computed value changed.  The compiler, RTL and stdlib needed no source
change.  Test churn: nine assertions on the resolved type of a builtin, and
one arm64 code-shape test that now includes the `Length` extension.

*4.5 — 64-bit length headers.*  The string header's Length and Capacity
fields and the dynamic-array length field become 64-bit, lifting the
2^31^ ceiling.  The header layout (24 bytes with a 64-bit RefCount for
natural alignment, or a 4-byte RefCount plus padding) is settled at the
start of the step by measuring both.  Affected: the RTL string and
dynamic-array routines, both backends' inline header reads
(`Length`, bounds checks, `for-in` over strings and arrays), string and
array literal emission in data sections, the internal assembler's literal
data, OPDF type records and pdr's string and array decoding.  A layout
change: full stage-2 rebuild protocol, `-pre` refresh, IFACE bump if any
`.bif` content encodes an offset, and the 4.4 run-time limit removed.

Done 2026-10-29, in three commits.

* Layout, settled at the start of the step.  Both refcount widths give the
  same 24-byte string header and the same atomic cost, so the choice was
  made on other grounds: the refcount stays a 32-bit atomic at
  `data_ptr − 12`, shared with the class refcount helpers (2^31^ live
  references to one string are not reachable), and Length moves to an
  `Int64` at its old offset `data_ptr − 8`.  String: Capacity at −24, pad,
  RefCount at −12, Length at −8 (24 bytes; data 8-aligned, up from 4).
  Dynamic array: pad, hook at −24, pad, RefCount at −12, Length at −8 (32
  bytes, so element 0 stays 16-aligned as the 16-byte header kept it).
* 4.5a, a refactor with no layout change: the seven RTL units that spelled
  header offsets out (three header-size constants and literal offsets)
  declare one named block of offsets and length types, and the RTL's
  lengths, positions and allocation sizes are `Int64`.  Found on the way and
  fixed: `_StringRelease` bounded a length by 1 GiB as a corruption check,
  so releasing a larger string aborted; `GetMem` / `ReallocMem` passed a
  32-bit size; the large-block header stored the size in 32 bits;
  `ReadFile` issued one `read`, which Linux caps near 2 GiB; the stdlib
  bound libc `memcpy` with an `Integer` count.
* 4.5b, the switch.  Both backends emit literal headers through one helper
  (`EmitStrLitHeader`, `.balign 8`) with the data at label +
  `STR_LIT_HDR` (24), read Length as 64 bits inline, take the RTL's
  `Int64` length and position results unextended, run `for-in` over a
  string or array with an `Int64` index, and pass element-hook counts and
  `_OrdAt` / `_Utf8DecodeAt` indices in 64 bits.  OPDF sets a new header
  flag, `LEN64` (4), in place of `DYNARRAY_LEN32`, and the string record
  carries the new offsets; pdr reads both.  `SetLength` zeroes new memory
  with `memset` instead of a byte loop.  `COMPILER_ID` is bumped; no IFACE
  bump was needed (no `.bif` content encodes a header offset).
* Bootstrap.  The rolling bootstrap builds each commit once with the
  previous commit's binary, and that binary's own code reads headers at the
  old offsets, so the RTL it links must keep the old layout.  The 4.5
  compiler predefines `BLAISE_HDR64`, and the RTL's layout blocks select on
  it: the RTL an older compiler builds is old-layout (consistent with that
  compiler's code), the RTL the 4.5 compiler builds is new-layout.  Only a
  compiler that predates 4.5b ever builds the old branch: the 4.5a binary
  does so when it builds 4.5b.  4.5c, a separate commit built by the 4.5b
  binary, removes the old branch and the predefine (teach in one commit,
  use in the next).

Tests: a dynamic array and a string of 2^31^ + 16 bytes are built, indexed
past 2^31^, measured and released
(`TE2ETypeStdTests.TestRun_LengthAboveInt32_Works`), and a 1.1 GiB string
is released (`TestRun_StringAbove1GiB_Releases`); the tests that read a
header offset or matched its instructions moved to the new layout.

*4.6 — collections (D5, part 2).*  `Count`, `Capacity`, indices and their
fields move to `Int` in `generics.collections`, `Classes` and `Contnrs`.
This is a field-layout change, so the full protocol applies: stage-2
rebuild before trusting anything, `-pre` refresh, `bif-coverage` and
`flag-coverage` baselines, and a pdr check that a `TList<T>` still prints
correctly.  No IFACE bump is expected (field types are serialised by name),
but confirm it with the warm-cache fixpoint.

*4.7 — `MaxInt`.*  Redefine `MaxInt` as `High(Int)`.  Audit its uses in
the compiler, RTL and stdlib: every use as a "to end of string" count in
`Copy` keeps working once 4.4 accepts an `Int` count; a use stored into a
32-bit variable would truncate to `-1` and must be retyped.

*4.8 — narrowing warning (opt-in).*  An opt-in warning,
`--warn-narrowing`, for an implicit integer narrowing on assignment or
argument passing (`I := Length(S)` with `I: Int32`).  It is opt-in because
the compiler's own source would produce thousands of instances until
Phase 5 retypes its index variables; Phase 5 uses it as a worklist, and it
may become a default warning after Phase 6.

=== Decisions on the open questions (2026-10-27)

. *64-bit string and array headers — part of Phase 4 (step 4.5).*  A
  64-bit `Length` result that cannot exceed 2^31^ would give a misleading
  answer to the question the widening is meant to settle, so the storage
  change belongs with the API change.
. *`MaxInt` — becomes `High(Int)` (step 4.7).*  The name refers to `Int`,
  so its value follows `Int`.  FPC familiarity is a weaker argument than a
  name that states its meaning.
. *Narrowing diagnostics — an opt-in warning (step 4.8).*  Silent
  narrowing remains the language rule; the warning is a migration aid.
. *Loop variables — the inference bullet is dropped.*  Blaise has no inline
  `var`, so a loop variable always has a declared type and Phase 5 retypes
  index variables to `Int`.  The question is revisited if inline `var` is
  ever adopted (undecided).
